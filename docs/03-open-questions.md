## 🔴 會影響架構決策

### Q1. 瀏覽器上每 hop 的固定開銷到底多少？

模型從 Petals 反解出約 **36 ms/hop**（Python + PyTorch + 原生 CUDA）。
瀏覽器 + WebGPU 的值目前是**猜的（預設 15 ms）**，而且方向不確定：
WebGPU dispatch 開銷可能更高，但少了 Python 與網路框架的負擔可能更低。

- **何時知道**：M2
- **答錯的後果**：直接決定 P 的上限。若瀏覽器是 50 ms/hop，
  P=8 光固定開銷就 400 ms/迭代，32B 以上的模型在 WAN 上基本不可用
- **怎麼量**：M2 時量「單 shard 執行時間」vs「經過一次完整 hop 的時間」的差

### Q2. 手機上的 $K^*$ 真的有 5–6 嗎？

roofline 推算手機級裝置的免費平行視窗約 5.5。但這個推算假設
WebGPU 能達到裝置標稱 FLOPS 的某個比例（模型裡設 1.5 TFLOPS 有效值），
而瀏覽器實際能壓出多少完全沒有驗證。

- **何時知道**：M2
- **答錯的後果**：$K^* < 3$ 的話，位置平行的效益空間太小，
  投機解碼路線要重新評估
- **注意**：$K^*$ 與切分方式無關（分子分母同步縮放），所以可以用單機量

### Q3. 激活值量化的誤差會隨切分數累積到什麼程度？

M1 已確認**未量化**時切分是完全無損的：固定輸入下 2/4/8/15 個 shard
的誤差是同一個數字（7.725e-05），殘差全部來自 ONNX 算子匯出而非切分。

但那是沒有 hop 量化的前提。加上每 hop 的 int8 量化後，
每一刀都會引入新的誤差，累積曲線是線性還是指數？

- **何時知道**：M4
- **答錯的後果**：若誤差隨 P 快速累積，大 P 配置就不能用 int8，
  傳輸量翻倍，WAN 可行性大幅下降
- **怎麼量**：固定模型與 `--seed`，掃描 P ∈ {2,4,8,16}，量 PPL 退化與 argmax 一致率

> ⚠️ **方法論教訓**：這個問題最初被誤答過。用未固定的隨機輸入比較不同切分數，
> 看到誤差上升就下了「會累積」的結論。實際上同一組態重複三次的變異
> （1.27e-4 ~ 2.74e-4）比跨組態的差異還大 —— 量到的是輸入雜訊。
> **任何跨組態比較都必須固定 `--seed`。**

## 🟠 需要一手查證（撰寫對外文件前必補）

### Q4. vanilla Jacobi / Lookahead / EAGLE 的確切加速倍數

目前用的是保守估計值（1.15 / 1.9 / 4.5）。
[00-feasibility.md §2.3](00-feasibility.md) 的敏感度分析顯示結論對這些數字
**不敏感**，但對外發布前每個數字都要有具名出處。

需要查證的論文：Santilli et al. 2023（vanilla Jacobi）、
Fu et al. 2024 arXiv 2402.02057（Lookahead）、
arXiv 2403.00835（CLLM）、EAGLE-2 / EAGLE-3、Medusa。

**特別注意**：要區分「每次 forward pass 產出幾個 token」和
「實際 wall-clock 加速」—— 很多論文只報前者。

### Q5. WebRTC DataChannel 在住宅網路間的實測吞吐上限

有報告指出 SCTP 擁塞控制實作會把吞吐壓在數十 Mbps。
若真是如此，模型裡「上行頻寬 = 節點標稱頻寬」的假設就錯了。

- **何時知道**：M3（同機測不出來，要 M6 真實 WAN）
- **答錯的後果**：傳輸時間被低估，大 K 配置不可行

### Q6. NAT 直連失敗率

「完全去中心化」的宣稱已經收回，但 TURN 的頻寬成本要能估算。
需要真實部署統計（Jitsi / Twilio / Cloudflare / 學術研究）。

### Q7. 各家瀏覽器的 WebGPU 可用顯存與 storage quota

文件中「手機 1.5–2 GB、筆電 4–8 GB」是估計值。
需要確認 `maxBufferSize` / `maxStorageBufferBindingSize` 的實際可協商上限，
以及 OPFS / Cache API 能否穩定存放數 GB 的權重。

- **答錯的後果**：直接決定 P 的下限（每節點塞得下多少）

## 🟡 已知但延後

### Q8. ORT Web 的 WebGPU EP 算子覆蓋率

M1 用的是 CPU EP。WebGPU EP 對某些算子支援不全，可能需要改寫匯出圖
或部分 fallback 到 WASM（效能會掉）。

- **何時知道**：M2

### Q9. KV cache 怎麼在 shard 之間管理

M1 刻意跳過 KV cache（每個 shard 吃完整序列重算）。
真實系統中每個 stage 要自己持有該層範圍的 KV cache，
而 churn 接手時新節點的 KV cache 是空的 —— 要重算還是傳過去？

- **何時知道**：M3（加入 KV cache）／ M7（churn）
- **傳過去的代價**：KV cache 遠大於 hidden state，可能不可行
  → 傾向「重算」，但那會讓 churn 接手有明顯停頓

### Q10. draft model 從哪來

投機解碼需要一個與 target model 同 tokenizer 的小模型。
現成的 draft model 不一定存在（尤其對較新的模型），
自己訓練 EAGLE-style draft head 的成本還沒評估。

- **何時知道**：M5
- **緩解**：Lookahead 是 draft-free fallback，效能較差但不需訓練
