## 🔴 會影響架構決策

### Q1. 瀏覽器上每段的固定開銷到底多少？ ⚠️ 部分回答

模型從 Petals 反解出約 **36 ms/hop**（Python + PyTorch + 原生 CUDA）。
瀏覽器 + WebGPU 的值目前仍是**猜的（預設 15 ms）**。

- **已知的一半**：真實裝置（Intel Xe-LPG 內顯）上，SmolLM2-135M 切 4 段，
  每段固定成本 **6.88 ms**（逐 shard 擬合截距直接量到，r² 全部 > 0.994）。
  開發容器的 WASM/CPU 對照組是 55.2 ms/段。
  交叉驗證：四段截距加總 27.859 ms vs 整條流水線截距 27.946 ms，差 0.087 ms。
- **為什麼還不算答完**：那是 135M 模型、**不含任何網路成分**的本機量測。
  而且該裝置上固定成本佔了 K=1 總時間的 78.7%，
  代表量到的是 dispatch 開銷主導的狀態，不是部署時的狀態。
  要回答這一題需要 1B 以上的模型（見 [00-feasibility.md §7.3](00-feasibility.md)）。
- **所以 `bench/model.py` 的 `overhead_ms` 維持 15 ms 不動** ——
  拿一個沒把握的實測值去換一個有把握的推算，不是進步。
- **答錯的後果**：直接決定 P 的上限。若瀏覽器是 50 ms/段，
  P=8 光固定開銷就 400 ms/迭代，32B 以上的模型在 WAN 上基本不可用
- **怎麼量**：✅ 已實作 —— `web/bench.html` 固定完整流水線、只掃序列長度，
  對每一段擬合 `耗時 = 固定成本 + 斜率 × 位置數`，截距就是固定成本。

  > **舊方法是錯的，記錄下來避免重蹈。** 原本用「把 4 段收成 2 段」製造不同
  > hop 數再做迴歸，但收起來的流水線會**跳過中間的層**，所以時間差裡同時混了
  > 「少幾個 hop」和「少算幾層」。等大小切分下層數與 hop 數完全共線，
  > 這個混淆無法靠多取資料點解決 —— 只能改量法。

  > **單位也錯過**：固定成本是**每段**付一次，不是每個交接。
  > 4 段之間只有 3 個交接，卻要跑 4 次 `session.run`。

### Q2. 手機上的 $K^*$ 真的有 5–6 嗎？ ❌ 問法本身在小模型上不成立

roofline 推算手機級裝置的免費平行視窗約 5.5。實測之後發現：
**在 135M 模型上，$K^*$ 這個量不存在** —— 不是量不準，是前提不成立。

- **實測（Intel Xe-LPG）**：`總耗時 = 27.95 + 4.23 × 位置數`，
  r² = **0.9994**，一條完美直線。
- **所以 `每位置耗時 = 27.95/k + 4.23` 對所有 $k$ 單調遞減，永遠沒有最小值。**
  「$K^*$ = 掃描上限」不管上限是 32、64 還是 1024 都會成立。
  第一輪看到 `censored` 就把上限從 32 放寬到 64 —— 那是治標，方向錯了。
- **根因**：固定成本佔 K=1 總時間的 **78.7%**，瓶頸是 `session.run` 的
  呼叫開銷而不是記憶體頻寬。$K^*$ 的定義前提（記憶體受限）不成立。

**改問一個答得出來、而且更有用的問題**：多算一個位置的邊際成本是多少？

- **邊際成本 4.23 ms**，對比第一個位置的 35.5 ms。
- **驗證視窗**：猜 8 個字一次驗證花 60.6 ms —— 單一 token 的 **1.71 倍**時間，
  卻驗完 8 個位置。只要 draft 接受率夠高，投機解碼就划算。
  這才是決定路線的數字，而 $K^*$ 不是。
- 報告用 `knee`（`observed` / `none-observed` / `unknown`）明確區分
  「沒有轉折點」與「掃描被截斷」，不再讓人誤以為拉高上限就能解決。

- **何時能回答原本的問法**：需要 1.7B 等級的模型（360M 只會把佔比從 79%
  降到約 71%，同一個區間）。線上量測頁維持 135M 是刻意的取捨 ——
  1.7 GB 不該壓在每個幫忙測試的人身上。想自己測的人用
  `MODEL=HuggingFaceTB/SmolLM2-1.7B npm run dev` 在本機跑。
- **注意**：$K^*$ 與切分方式無關（分子分母同步縮放），所以可以用單機量

### ~~Q11. 數值等價性是否逐 execution provider 成立？~~ ✅ 已答（M2）

**結論：跨 EP 差異 3.78e-4，比各自對參考值的誤差小一個數量級以上，
argmax 完全一致。不需要強制全網統一 execution provider。**

| | 對 native 參考值 | 對 WASM |
|---|---|---|
| WASM EP | 7.88e-3 | — |
| WebGPU EP | 8.10e-3 | **3.78e-4** |

兩者 argmax 都 16/16 全對（Intel Xe-LPG，SmolLM2-135M int8 切 4 段）。

⚠ **保留**：這是 4 段 / 3 hop 的結果。Q3（§6.3）量到誤差會隨 hop 數
**次線性累積**，14 hop 時跨 EP 差異會放大多少還沒量過 —— 混用前要先驗。

以下是原始問題的記錄：



規劃 M2 時實測發現：同一組 shard 在**原生 ORT**（CPU EP）的誤差是 7.725e-05，
在 **ORT-Web 的 WASM EP** 是 1.965e-4 —— 差一個檔次。
**數值行為是跟著 EP 走的。**

這代表「等價性」不能只驗一次就當全域成立，必須**逐 EP 宣告與驗證**。
WebGPU EP 的數值行為目前完全未知。

- **已知的一半**：ORT-Web WASM EP 在瀏覽器中實測 **1.502e-04**
  （原生 ORT CPU EP 是 7.725e-05），argmax 完全一致。
  所以 WASM EP 雖然誤差大一個檔次，但不影響貪婪解碼的選字。
- **~~未知的一半~~**：WebGPU EP 已量到（見上方結論）
- **答錯的後果**：若不同節點用不同 EP（有的 WebGPU、有的 WASM），
  流水線可能在節點之間產生不一致。可能需要強制全網統一 EP，
  或把容忍度納入投機解碼的驗證邏輯

### ~~Q3. 激活值量化的誤差會隨切分數累積到什麼程度？~~ ✅ 已答（M4）

**會累積，但是次線性的。** 最佳方案（per-channel + 前 3% 通道 fp16）的
argmax 一致率：1 hop 99.37% → 14 hop 98.24%。hop 數增加 14 倍，
不一致率只放大 2.8 倍。完整數據見 [`data/quant-results.md`](data/quant-results.md)。

順帶回答了原本擔心的「小模型看不到離群現象」——
**135M 的離群比值就有 1212×**，遠超文獻對 6–7B 報告的 20–100×，
所以這個結論在此規模是可信的，不需要 7B+ 重測。

> ⚠️ **方法論教訓**（保留，因為它適用於所有後續里程碑）：
> 這個問題在 M1 階段被誤答過一次。用未固定的隨機輸入比較不同切分數，
> 看到誤差上升就下了「會累積」的結論。實際上同一組態重複三次的變異
> （1.27e-4 ~ 2.74e-4）比跨組態的差異還大 —— 量到的是輸入雜訊。
> **任何跨組態比較都必須固定 `--seed`。**

### Q5. 每一次突發傳輸要付多少 cwnd / slow-start 的代價？（原問題已重新界定）

原本的問法是「SCTP 擁塞控制會不會把吞吐壓在數十 Mbps」。
**追查出處之後，那個前提站不住了。**

那個說法的源頭是 Eskola & Nurminen 2014 的量測，量的是
**Chromium 38 / Firefox 33**。它的機制是當時實作寫死的 **128 KiB 接收視窗**
—— 視窗 ÷ RTT 就是吞吐天花板，所以在數十毫秒的 RTT 下自然卡在數十 Mbps。
那是一個**實作參數**，不是 SCTP 這個協定的性質。
今天 Chrome 用的 dcSCTP 宣告的接收視窗是 **5 MB**，大約 40 倍，
原本那條天花板已經不存在了。

> **教訓（與 Q1、Q3 同一類）**：一個十年前的數字被轉述時，
> 留下來的是**結論**（「數十 Mbps」），掉的是**機制**（「128 KiB 視窗」）。
> 而機制才是判斷它今天還成不成立的唯一依據。
> 引用舊量測時要把機制一起抄下來，否則就是在引用一個沒有保存期限標示的數字。

**所以真正還沒答的問題不是穩態頻寬，是延遲。**

這個專案的流量長相是**一連串小突發** —— 每 hop 幾十 KB 的激活值，送完就等對面，
不是拿一條連線持續灌滿。這種形狀**根本走不到穩態**：每次突發都還在 slow-start 裡，
付的是「cwnd 還沒長起來」的代價；而且連線閒置一陣子之後 cwnd 會被重置，
下一次突發得從頭再爬一次。回程那 3 MiB 的 fp32 logits
（[01-architecture.md §4.5.7](01-architecture.md)）更是直接踩在這件事上。
會不會痛取決於 cwnd 的成長速度與閒置重置策略，**和接收視窗有多大無關**。

- **何時知道**：**M6，不是 M3。**（原本這一行寫的是
  「M3（同機測不出來，要 M6 真實 WAN）」—— 它自己否定自己，
  等於沒有排程，所以真的沒有人去排。現在直接寫 M6。）
  M3 全程走 loopback 或同一個 LAN，RTT 接近 0，slow-start 幾乎沒有代價可付；
  在那裡量出來的數字**一定好看，而且一定沒有意義**。
- **M3 該做、也只該做的一件事**：把每趟 traversal 的位元組數與耗時如實記下來，
  讓 M6 有同一套量法可以對照。**不要在 M3 對頻寬下任何結論。**
- **答錯的後果**：傳輸時間被低估、大 K 配置不可行 ——
  但後果的形狀變了：不是「頻寬不夠」，而是「每一趟都要重新暖機」。
  兩者的對策不同（前者是壓縮，後者是保持連線熱著、或把小訊息合併）。

### Q7. 各家瀏覽器的 WebGPU 可用顯存與 storage quota ⚠️ 一筆資料點

文件中「手機 1.5–2 GB、筆電 4–8 GB」是估計值。
需要確認 `maxBufferSize` / `maxStorageBufferBindingSize` 的實際可協商上限，
以及 OPFS / Cache API 能否穩定存放數 GB 的權重。

- **第一筆（Chrome / Intel Xe-LPG）**：`maxBufferSize` 2 GB、
  `maxStorageBufferBindingSize` 約 2 GB —— 都遠高於 WebGPU 規格的預設下限
  （256 MiB / 128 MiB），單層權重塞不下的疑慮在這台機器上不存在。
  儲存配額 10.7 GB，足夠放 32B/P=4 的單節點份額（約 4 GB）。
- **還缺的**：手機、Safari、AMD/NVIDIA 獨顯。一台筆電的內顯不能代表全部。
- **答錯的後果**：直接決定 P 的下限（每節點塞得下多少）

### Q8. ORT Web 的 WebGPU EP 算子覆蓋率

M1 用的是 CPU EP。WebGPU EP 對某些算子支援不全，可能需要改寫匯出圖
或部分 fallback 到 WASM（效能會掉）。

- **何時知道**：M2

### Q9. KV cache 怎麼在 shard 之間管理

M1 刻意跳過 KV cache（每個 shard 吃完整序列重算）。
真實系統中每個 stage 要自己持有該層範圍的 KV cache，
而 churn 接手時新節點的 KV cache 是空的 —— 要重算還是傳過去？

- **何時知道**：**M5**（加入 KV cache）／ M7（churn）
  —— KV cache 已從 M3 移進 M5，理由見 [02-roadmap.md](02-roadmap.md) 的 M3 一節
- **傳過去的代價**：KV cache 遠大於 hidden state，可能不可行
  → 傾向「重算」，但那會讓 churn 接手有明顯停頓

### Q10. draft model 從哪來

投機解碼需要一個與 target model 同 tokenizer 的小模型。
現成的 draft model 不一定存在（尤其對較新的模型），
自己訓練 EAGLE-style draft head 的成本還沒評估。

- **何時知道**：M5
- **緩解**：Lookahead 是 draft-free fallback，效能較差但不需訓練
